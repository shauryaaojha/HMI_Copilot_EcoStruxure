# HMI Panel 1 (real training rig)

A real project, `auto-manual.eote`, from Schneider's "HMI Panel - 1" demo
rig: "HMI for Device Control & Monitoring with Web Server Functionality". It
is the first project in this repo that was made by an engineer for real
hardware rather than generated by us, and it is the test for whether our
screens run on a panel.

## The hardware (from photos of the rig, 2026-10-30)

| Device | Part | Address | Role |
|---|---|---|---|
| HMI | HMIST6600 (Harmony ST6, 1280x800) | 192.168.10.1 | Operator panel, also web server for a PC dashboard |
| PLC | TM251MESE (M251) | 192.168.10.2 | Runs start/stop and speed logic |
| Drive | ATV340U07N4E (0.75 kW Altivar Machine) | Ethernet, behind the PLC | Speed control of the motor |
| Switch | Ethernet switch | | HMI, PLC and drive on one network |
| Motor | CG Power 3-phase induction motor | | Load |
| Power | ABL8RPS24050 24 VDC 5 A PSU, xC60 breakers MAIN C10, ATV340/PSU/HMIST6600/M251 C6 | | |

The board says Modbus TCP between the switch, PLC and drive, but the PLC's
symbols include `IoConfig_Globals.Altivar_340` of type `FB_Atv340EthernetIP`,
so the PLC program drives the ATV340 over EtherNet/IP. The HMI does not talk
to the drive at all. It talks **Machine Expert network protocol** to the M251 and
reads the PLC's own symbols (see below).

## The project

- Made in OTE **4.1.0.89** (created 2025-09-18, last saved 2026-10-30). Target `HMIST6600`, 1280x800 landscape, web server on, transfer to 192.168.10.1.
- Driver: `MachineExpertNetwork1` (SoMachineNetwork V1.6.7.8, TCP on Ethernet1). Equipment: `MachineExpertEquipment1` at 192.168.10.2, port 11740, node `TM251MESE @0000547DF861`, symbol link on. The symbol file was imported from `EEE PLC_Machine_Modify25042020.MyController.Application.xml`.
- Screens: `Folder1` (master screen with Home, Bell and Gear icons that switch to screen 1, 3 and 4, title "HMI PANEL 1", date and time), `Screen1` (four content displays, an Auto/Manual toggle, the reference frequency), `Screen2` (system alarm summary), `Screen3` (hardware configuration).
- Contents: `Start_Stop` (START, STOP/READY and RESET push buttons on `Run_CMD`, `Stop_CMD`, `Flt_Reset`, a drive status text), `Frequency_Set`, `Meter` (gauges for voltage and speed), `Bar_Graph` (current, power, thermal state, voltage).
- Scripts: every 100 ms a global script copies Motor_Voltage, Output_Velocity, Motor_Current, Motor_Thermal_State and Motor_Power into the HMI tags Var1 to Var5. A periodic script on Start_Stop sets `Drive_Status` from `Status_Reg`: 561 "Ready", 568 "Fault", 1591 "Run", 592 "Not Ready".
- No alarms of its own (Alarm.db is empty); only the system error group is shown.
- 11 compound objects from the Pro-face library (BarGraph_Vert, Switch_PB04, Gauge_10, Display_ND01).

## The tags

`tags.csv` is the 35 tags an operator screen would use, extracted from
`Variables.db` (162 rows in all: the rest are PLC housekeeping such as
compiler and runtime versions, I/O configuration, timer members and bit/word
helpers). The project carries no comments; the ones in the CSV only say where
a tag lives, plus what the project's own scripts show. The engineering units
and ranges of the GVL words are not in the file and need the M251 program.

- **GVL** (drive values the PLC reads from the ATV340): Motor_Freq, Motor_Current, Motor_Voltage, Motor_Power, Motor_Torque, Motor_Thermal_State, Drive_Thermal_State, Mains_Voltage, Output_Velocity, Reference_Freq, Reference_Frequency, Speed_Setvalue, Motor_Run_Time, Power_On_Time, Status_Reg, CMD_Reg, Communication_Status. All WORD.
- **Main** (commands and states): Run_CMD, Stop_CMD, Flt_Reset, Direction, Fault, Ready, Ready_To_SwitchOn, Running, AUTOMAN, AUTOSTART, AUTO_SEQ_OFF (BOOL), Frequency_Set (WORD).
- **HMI internal**: Drive_Status (STRING), Var1 to Var5 (WORD).

## How a PLC symbol is bound (the reverse-engineered part)

A symbol tag is not bound by its bare name. Bindings.dat names it by folder
path, and carries the folder ids:

```
Source  ObjectType 4, ObjectFullName "MachineExpertEquipment1.GVL.Motor_Current",
        ParentIds "<MachineExpertEquipment1 folder id>,<GVL folder id>"
Binding BindingText "MachineExpertEquipment1.GVL.Motor_Current.Value"
```

A structure member adds its root variable and its parent ahead of the folders
(`MachineExpertEquipment1.Main.AUTOOFF.IN`, ParentIds `<AUTOOFF>,<root folder>,<Main>`).
The rule was checked on every variable source in this file (175) and in the
template corpus (980 in all). Every symbol tag also has a ScanRate binding
to `DefaultScanRate`. The reader and writer follow the rule
(`web/src/lib/ote/reader.ts` refOf, `bindings.ts` VariableRefs), and
`web/tests/real-panel.test.ts` holds it.

## Generate screens into it

```
cd web
npx tsx --tsconfig scripts/tsconfig.json scripts/panel1.mts
```

This opens the project, runs the generation pipeline on the process tags,
adds the screens beside the engineer's, and writes
`demo_project/HMICopilot_Panel1.eote`. The PLC connection, the tag database,
the scripts and the existing screens are not touched.

## Opening our screens on the lab's OTE 4.1

An export from the app is saved as OTE 4.4, which 4.1 will not open. Move its
screens into this 4.1 project instead:

```
cd web
npx tsx --tsconfig scripts/tsconfig.json scripts/into-project.mts <our export.eote> ../samples/hmi-panel-1/auto-manual.eote ../demo_project/<name>_4.1.eote --replace
```

This writes `demo_project/<name>_4.1.eote`: only our screens (with their own
screen numbers, 1 being the start screen) on this project's Project.dat
(4.1.0.89), driver, tags and global script. Bindings are rewired to the PLC
symbols with the same names; any to tags the project lacks are dropped and
listed. Without `--replace` our screens are added beside the engineer's.
`--only Drive,Alarms` takes just the named screens of the export.

`demo_project/HMICopilot_Drive_4.1.eote` is the app's screen for this rig's
tags, made that way: one Drive faceplate (Id 1), 37 bindings.

## What the app now makes from these tags

- One drive, not 21 instruments: a small list with no loop numbers that names
  one machine (a motor with a frequency is on a drive) is one faceplate screen,
  so there are no overflow `_2.._n` screens and START and STOP sit together.
- START / STOP / RESET are momentary push buttons (ClickTrigger Operation 10),
  bound through `ClickTrigger.Destination`, Mode 1, as the product writes them.
  Before this they were bound to `CurrentValue` and wrote nothing.
- AUTOMAN is a MANUAL / AUTO toggle switch.
- Speed_Setvalue and Frequency_Set are entry boxes. Every other number is
  read-only (`IsInputModeEnabled: false`); before this an operator could type
  into a current reading.
- Navigation chips change screens (ClickTrigger OperationType 4, by the
  target's screen number).
- Not matched yet: the engineer's look (Pro-face compound objects, master
  header). Ours is the grey ISA-101 style.

## Testing on the panel

1. Open `auto-manual.eote` in OTE and download it unchanged: the baseline should run exactly as it does today.
2. Open `demo_project/HMICopilot_Drive_4.1.eote` (only our screen) or `demo_project/HMICopilot_Panel1.eote` (beside the engineer's) in OTE. Check: it opens without errors, the new screens are listed, and Validate is clean.
3. The new screens are not linked from Screen1 or the master header yet. For the test, add a Switch Screen button on Screen1 to `PlantOverview`, or set it as the start screen.
4. Download to 192.168.10.1 with the PLC running. Start the motor from the existing Start_Stop screen and check that the new screens show the same frequency, current and voltage as the engineer's gauges.
5. If the lab's OTE is 4.1, check that it opens our file. We write 4.4-style objects into a 4.1 project; that has not been tried.
