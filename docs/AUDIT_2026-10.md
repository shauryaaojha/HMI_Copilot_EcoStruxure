honest Vijeo path is the one Schneider's answer 6 implies: the tags come in

## 3 · Bugs fixed (each with a failing-then-passing test)

1. **Alarms of a second group were moved and reset on any alarm edit.** The
   reader modelled every `Alarm` row under the first group's name, and
   `syncAlarms` re-inserted them all there with `Deadband` and `Parameter` set
   to 0. Now only the first group is modelled, and a kept alarm keeps its own
   row and `UniqueId`. *(test fails on the old code: ran)*
2. **A damaged `Bindings.dat` would have exported with every binding
   dropped.** It is now refused as `damaged`. A damaged `Screen.dat` no
   longer fails the whole open; that screen is carried with a warning.
3. **OTE's own XLSX export read the `Summary` sheet as tags.** The importer
   now reads `Variables`, and finds a header under a preamble.
4. **Vijeo's CSV export skipped every row.** The leftmost-alias header match
   took the row-kind column as the data type.
5. **`x-file-name: %E0`** threw outside the `try`: a 500 on every import route.
6. **The level alarm on `LT_101` was worded "Pump 101 level high"** (found by
   the new scanner in `HMICopilot_Bars.eote`). It now names what is measured.

Also: export preflight (every defect at once as a 422, names compared
case-sensitively per OTE's own naming rules, *installed help*); a read-back
self-check before download; a ZIP guard that checks declared sizes before
inflating; typed `IngestError`s with hints everywhere; and safe client-side
JSON handling for HTML error pages.

## 5 · Edit the screen, or regenerate it and delete the old one?

**Edit. Regenerate only the generated layer, and never by delete-and-recreate.**

Deleting a screen and generating a new one changes every `UniqueId` on it. In
an OTE project those ids are referenced from `Bindings.dat` (Targets carry
`ObjectId`, `ParentIds`, `ScreenId`), from navigation and screen-change
switches, and by name from Lua scripts. A delete-and-recreate therefore:

- breaks the byte-identical round trip the reader is built to protect;
- silently re-points or orphans anything the tool does not model (scripts,
  carried objects, content displays);
- throws away every hand edit, which is exactly what makes an engineer stop
  trusting the tool after the first time.

The design that keeps both properties:

1. **Give every generated object a stable key**, not just a name:
   `(equipment id, role, slot)`. The pipeline already names parts this way
   (`Card_PMP101`, `Lamp_PMP101_RUN`).
2. **Record provenance** in `ObjectMeta`: `origin: "generated" | "edited" |
   "manual" | "imported"`, set to `edited` by any store action that touches a
   generated object.
3. **Regenerate one screen as a diff**: compute the new program, match by
   key, and show added / changed / removed. Objects marked `edited`,
   `manual` or `imported` are untouchable by default, and a matched object
   keeps its `UniqueId` so its bindings and references survive.
4. **Accept per object**, using the proposal UI that already exists.

Delete-and-regenerate is right in one case only: a project with no hand work
and no export yet. That is what `startOver` already is, behind a
confirmation.

> **Built, 7 October 2026.** Every step above is in: recipes per screen
> (`store.programs`, the `program` event), stable keys from the Placer,
> provenance in `ObjectMeta`, `lib/program/recompile.ts` +
> `/api/regenerate`, the pure diff in `lib/program/regenerate.ts`, the
> undoable `store.applyRegeneration`, and a side panel (the refresh button
> on the active screen's tab) that edits the recipe, lists every change
> with its reason, draws ticked changes as ghosts, and applies them. Proven
> on live routes: a freshly generated screen recompiles to zero changes;
> a hand-drawn screen is refused with `no-recipe`. `tests/regenerate.test.ts`.
