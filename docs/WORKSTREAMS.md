# Two parallel workstreams

Two Claude Code sessions, two machines, one repo, no conflicts.

| | **FORMAT** | **SURFACE** |
|---|---|---|
| Machine | Windows laptop | Mac |
| Owns | everything that touches the `.eote` | everything the engineer sees |
| Can verify | that a generated project opens in OTE | that the UI renders and behaves |
| Phases | 1, 2b, 3-backend, 4-backend, 6-rules, 7 | 0, 2, 3-frontend, 4-frontend, 5, 6-UI, 8, 9 |

---

## Why the split falls this way

**EcoStruxure Operator Terminal Expert 4.4 is Windows-only.** The Mac cannot run
`setup:skeleton` or `index:graphics`, cannot read `PropertyDefinitions/`, and — the
part that matters — cannot confirm that a generated file actually opens.

So format truth lives on the laptop, and it is not a preference: any claim about the
`.eote` that has not been opened in the product is unverified. The Mac builds against
committed fixtures that came out of a file which *was* opened.

The Mac is unblocked. `npm install && npm run dev` renders the real pump-station
screen from `src/fixtures/`, lifted straight out of
`demo_project/HMICopilot_PumpStation.eote`. No installation needed.

## The type system enforces the one rule

`ScreenRenderer` switches exhaustively over the part union. When FORMAT adds a part to
`schema.ts`, **the Mac's canvas stops compiling until it renders that part.** That is
deliberate: it is "the canvas may only render what the packager can emit", enforced by
`tsc` instead of by discipline.

The reverse is also true. SURFACE cannot invent a visual, because there is no schema
case to render it from.

## Git

Both sessions work on `main`. Because the file sets are disjoint, rebases never
conflict.

```bash
git pull --rebase origin main     # before you start, and before every push
git add -A                        # safe: you only edited your own files
git commit -m "..."
git push origin main              # if rejected, pull --rebase and push again
```

Commit small and often — a rejected push after four hours of work is the only way this
goes wrong. Do not add Claude as a co-author.

## FORMAT — the task list

Order matters. Phase 1 gates everything.

### 1. Port the packager  —  **DONE** (branch `format/packager`)

`packager.ts`, `databases.ts`, `bindings.ts`, `parts.ts`, `skeleton.ts` and
`demo-project.ts` are in place. Nine tests pass, including a structural diff against the
project `tools/make_project.py` produces.

**Still open:** somebody has to open `demo_project/HMICopilot_TS.eote` in OTE 4.4. That
is the half of the gate a test cannot cover.

Two traps, both already paid for once:

- ZIP entry names use **backslash** separators. Verify against the raw bytes
  (`text.includes("Screens\\")`), never against the library's own name list.
- Quote every SQL column. `Order` and `Value` are keywords, and SQLite returns an
  unknown double-quoted identifier as a **string literal** rather than erroring.

### 2. Export route (Phase 7)  —  **DONE bar the report**

`POST /api/export` returns a real `.eote`, verified against a production build. The HTML
validation report is still to add, once Phase 6's rules exist.

### 3. Symbol library (Phase 2b)

`npm run index:graphics` already converts 474 of 475 shipped objects with no geometry
errors. Remaining work: the packager emits a `Path` part, and a round trip through
export and re-open in OTE preserves it. Replace `placeholderSymbols` in
`src/fixtures/index.ts` with the real index for local work — it stays gitignored.

### 4. Tag ingestion (Phase 3, backend)

`POST /api/tags/parse` — SheetJS over `.csv` / `.txt` / `.xlsx` and Machine Expert
symbol files → `Variable[]`, naming rules applied with corrections **reported, not
silent**.

### 5. Generation pipeline (Phase 4, backend)

`POST /api/generate` streaming the events in `src/types/events.ts`. Claude
`claude-opus-5` via `@anthropic-ai/sdk`, `messages.parse()` with `zodOutputFormat`
against `schema.ts` so an invented property cannot survive parsing. Emit **one complete
object at a time** — never partial JSON.

### 6. Validation rules (Phase 6, backend)

`lib/validation/rules.ts` — naming conventions, binding integrity, type mismatch,
completeness, standards conformance. Findings carry an `objectId` so the UI can link
them.

### 7. Keep the fixtures fresh

After any change to `make_project.py`:

```bash
python tools/make_project.py demo_project
python tools/export_fixtures.py
```

That is the handoff to SURFACE. Say so in the commit message.

## SURFACE — the task list

Everything here works today against `src/fixtures/`. Nothing waits on FORMAT.

### 1. Design system and shell (Phase 0)

Tokens are in `globals.css`, read off `docs/ui-reference/`. Build out:

- UI primitives — `Button`, `Input`, `Select`, `Tabs`, `Panel`, `Badge`, `Toggle`, `Field`
- `TopBar` and `NavRail` exist as skeletons; bring them to the reference renders
  (icons via `lucide-react`, project name, saved state, target panel, theme toggle)
- resizable three-pane layout with `react-resizable-panels`

Remember: the application chrome is ours and is dark. **The HMI screen on the canvas is
never themed by us** — its colours come from the project palette. Theming it would
break the "preview cannot lie" claim.

### 2. The canvas (Phase 2)  ← the hero

`ScreenRenderer` renders the fixture today. Bring it to the reference:

- selection handles, hover highlight, marquee select
- zoom / pan / fit, grid, snap
- the `AlarmSummary` part properly (it needs the alarm list, not just the object)
- `<GraphicObject>` for `Path` parts — use `placeholderSymbols` until FORMAT lands the
  real index; the shape of an entry will not change

The comparison that matters: rendering the fixture should match
`assets/screen_design.png`, which the Python renderer produced from the same JSON.
Getting those to agree *is* the "two renderers" claim.

### 3. Intent panel and tag UI (Phases 3–4, frontend)

- the describe box, quick prompts, file drop
- the tag table and summary panel from reference screen 3
- consume the SSE stream from `/api/generate` — the event contract in
  `src/types/events.ts` is frozen, so this can be built against a mock emitter before
  the route exists

### 4. Build timeline (Phase 4, frontend)

Steps plus the live log pane. Engineering language, never "Thinking…". Each step
clickable and highlighting what it produced.

### 5. Inspector (Phase 5)

Property groups per part, generated from the zod schemas rather than hand-written per
type — a part gains an editor the moment it gains a schema. Edits write back through
`useProject.updateObject`.

### 6. Binding map and validation UI (Phase 6, frontend)

`demoBindings` has the real graph. Port the layout from
`tools/make_binding_map.py` / `assets/binding_map.png`: tags left, properties right,
connectors between, filters, unbound amber.

### 7. Simulation (Phase 8)

`lib/sim/engine.ts` — tick values, cross setpoints, fire alarms. `demoLiveValues` is
the target state; `assets/screen_live.png` is what it should look like.

### 8. Supporting screens (Phase 9)

Landing, Projects, Templates, Library, Standards, History, Settings — reference screens
1, 2, 4, 5, 10, 11, 12.

## The seams, and who owns each side

| Seam | FORMAT provides | SURFACE consumes |
|---|---|---|
| Screen objects | `schema.ts` part union | exhaustive switch in `ScreenRenderer` |
| Generation | SSE events from `/api/generate` | timeline, canvas, binding map |
| Tags | `Variable[]` from `/api/tags/parse` | tag table, summary |
| Validation | findings with `objectId` | results list, click-to-object |
| Export | `.eote` bytes from `/api/export` | the export dialog |
| Symbols | `graphics-index.json` | `<GraphicObject>` |

Every one of these is already typed. Build against the type, not against the other
session.
