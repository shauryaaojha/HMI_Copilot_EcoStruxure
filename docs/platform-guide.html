Section 01

The world this lives in

An HMI is a Human–Machine Interface: the touchscreen bolted to the front of a control cabinet that an operator looks at all shift. It shows whether pump 1 is running, what the tank level is, and what has gone wrong.

It is not the thing doing the controlling. The controlling is done by a PLC — a Programmable Logic Controller, an industrial computer that reads sensors and drives motors and valves on a cycle of a few milliseconds. The HMI is a window onto the PLC's memory. That distinction is the single most useful thing to hold on to: the PLC decides, the HMI displays.

01

Field device

A flow meter on a pipe, a level probe in a tank, a motor starter. Produces a signal.

02

PLC

Reads every input, runs the control logic, writes outputs. Holds the result in named memory.

03

Tag

One named piece of that memory — FT_101_PV. This is what both sides agree on.

04

HMI panel

Polls the PLC over a fieldbus and paints the value onto a screen object.

05

Operator

Sees a number move, a lamp turn green, an alarm appear. Acts on it.

The tag is the contract. Everything our project does happens at step 03 → 04.

Who is actually involved

RoleWhat they doWhat they feel

HMI engineer Draws every screen and wires every tag to every object, by hand. This is the job HMI Copilot is aimed at. Hundreds of bindings per project.
Commissioning engineer Takes it to site, downloads to the panel, makes it work against real hardware. Discovers the mistakes. On site, under time pressure, with the customer watching.
Operator Uses the finished HMI every day. Never sees the engineering. Just needs the screen to be right.
System integrator / OEM The company delivering the whole panel. Often builds 40 near-identical machines. Pays for the repetition. Wants consistency across engineers.
Why this problem is worth money

An HMI engineer hand-places every lamp and hand-types every binding, then repeats it for the next near-identical machine. A single wrong binding is invisible until commissioning — and by then the panel is on a customer's floor and the fix costs a site visit.

Section 02

EcoStruxure Operator Terminal Expert

EcoStruxure is Schneider Electric's umbrella brand for its industrial software and hardware. Operator Terminal Expert — OTE — is the specific product for designing HMI screens. Version 4.4 is what we target.

OTE is two programs that ship together, and confusing them is the most common misunderstanding. They run on different machines, in different languages, at different times.

Runs on the engineer's PC

Buildtime

The editor. Where a human draws screens, declares variables, configures alarms and wires bindings. Produces a project file. Nothing here talks to real hardware.

We produce the file it opens. We never modify the program.

The workflow OTE expects

  1. Create a project and pick a target panel model, which fixes the screen resolution.
  2. Declare variables — every tag the HMI will read, with its data type.
  3. Draw screens — drag parts from the Tool Chest onto a canvas.
  4. Bind each object property to a variable, one at a time.
  5. Configure alarms against trigger tags and thresholds.
  6. Validate, then download to the panel.
The insight the whole project rests on

Steps 2–5 are mechanical. They are determined by the tag list plus engineering convention — a pump gets a run lamp and a fault alarm, a level gets a numeric display and a high-level alarm. That is knowledge, not creativity, and knowledge can be encoded.

Panel model names, decoded

A model string like HMIST6500AWADI looks like noise but is a spec sheet. Ours is a Harmony ST6 series, 10-inch, wide, analogue-resistive touch.

Resolution1024 × 600, landscape — fixed by the model, stored in Target.dat

This matters because a screen is authored at the panel's exact pixel size. Ours is 1024 × 600 because the target says so — not because we chose it.

Reading a tag name

Tag names are not arbitrary. Most plants follow ISA-5.1, an instrumentation standard that gives every measuring device a letter code. Once you can read it, a tag list tells you what the plant physically contains.

So FT_101_PV is the live flow reading from the flow transmitter on loop 101. And because PMP_101_RUN, PMP_101_FLT and FT_101_PV share loop 101, they describe one pump and its instrumentation. That shared middle number is exactly what lets a machine infer equipment from a tag list.

Data types — IEC 61131-3

IEC 61131-3 is the international standard for PLC programming languages, and it fixes the type names. OTE uses them directly.

A trap that costs a commissioning day

A REAL bound to a lamp is a type mismatch: the lamp expects BOOL. OTE will accept the project and the error appears as a lamp that never changes. Our validator catches this at design time, which is the entire point of the exercise.

Section 04

How alarms work

An alarm is a named condition the panel watches continuously and announces when it becomes true. OTE stores them in Alarm.db, grouped, and each one is bound to a trigger tag.

Two kinds, and they are configured differently

AlarmRecordType 1

Bit alarm

Fires when a BOOL goes true. There is no threshold — the PLC already decided.

Example
PMP_101_FLT → "Pump 1 fault"
IsOnTrigger
1

AlarmRecordType 2

Level alarm

Fires when a numeric tag crosses a setpoint. The threshold lives in the alarm, not the PLC.

Example
LT_101_PV > 85 → "Tank level high"
IsOnTrigger
0

Severity levels — HiHi, Hi, Lo, LoLo

Process alarms come in nested pairs. Hi is "pay attention", HiHi is "act now"; Lo and LoLo mirror them downward. A tank typically has all four: too empty to pump, and too full to fill.

NameAlarmTypeMeaningIn our demo
HiHi1critical high — interveneLT_101_PV > 95
Hi2warning highLT_101_PV > 85
Lo3warning low—
LoLo4critical low—

The lifecycle an operator sees

StateShortWhat happened
ActiveACTThe condition is true right now.
UnacknowledgedUNACKNobody has pressed acknowledge yet. Usually flashing.
AcknowledgedACKAn operator has seen it. Stops flashing, stays listed.
Return to normalRTNThe condition cleared.

Deadband is the hysteresis that stops an alarm chattering: once fired at 85, it will not clear until the value drops meaningfully below 85.

Section 05

Inside a .eote file

A .eote is a ZIP archive of plain JSON and plain SQLite. No encryption, no signature. That single fact is what makes the whole project possible.

project.eoteZIPentries use BACKSLASH separators
 ├─ Project.datJSONidentity, version, theme
 ├─ Target.datJSONpanel model and resolution
 ├─ Variables.dbSQLITEthe tags
 ├─ Alarm.dbSQLITEalarm groups and alarms
 ├─ Recipe.db, Security.db …SQLITEsubsystems we copy through untouched
 ├─ Bindings.datJSONSources → Bindings → Targets
 ├─ Screens\Hierarchy.datJSONscreen order
 └─ Screens\<guid>\one folder per screen
    ├─ Screen.datJSONthe object tree — every part on the screen
    ├─ Metadata.datJSONscreen name and order
    └─ LocalVariables.dbSQLITEvariables scoped to this screen

Four properties that make automation possible

  1. Everything meaningful is JSON or SQLite. Screen.dat is a tree of Type / Children / Location / Width / Height. It generates and diffs like any document.
  2. No signature, no encryption. Every project carries EncryptionInfo: null and SignatureInfo: null. Nothing has to be defeated — there is nothing there.
  3. Bindings are declarative. Wiring a tag to a display is one JSON object, not code.
  4. Geometry maps onto the browser. Parts are absolutely positioned inside a ViewBox — a direct match for absolutely-positioned SVG.

Colours are palette indices, not RGB

A screen never stores #00B050. It stores 3, an index into the project's colour set — ours is ColorSet 4, "Green-Simple", defined in the product's own Colors.lua. Change the project's palette and every screen follows. It is why a generated screen matches house style by construction.

The trap that ate three hours

ZIP entry names use backslash separators, the way the product writes them. Python's zipfile silently rewrites them to forward slashes. And in a TypeScript string, "Contents\Hierarchy.dat" contains \H — not a valid escape, so the backslash is simply dropped and the entry silently becomes ContentsHierarchy.dat.

Both failures are silent. Verify entry names against the raw bytes, never against a library's own name list.

Section 06

The binding graph

This is the file that does the work the problem statement calls "complex tag integration". Understand this and you understand the product.

Bindings.dat holds three arrays. Sources are tags. Targets are things that can be driven. Bindings join them by index. One tag can drive many targets — which is exactly where hand-wiring goes wrong.

Section 07

What HMI Copilot does

A PLC tag export plus one sentence of plain English becomes a complete, validated EcoStruxure project — screens drawn, tags declared, alarms configured, bindings wired — while the engineer watches each object appear and approves it.

The pipeline

#StepWhat it doesLives in
1IngestParse the tag export; normalise names and types; report every correction.lib/tags
2Infer equipmentCluster tags by loop number. PMP_101_* becomes one pump.lib/ai
3Select partsChoose real OTE part types — a BOOL gets a Lamp, a REAL a NumericDisplay.lib/ote/parts
4Lay outPosition parts absolutely inside a ViewBox sized to the panel.lib/ai
5Generate alarmsEvery fault tag gets an alarm; every level gets Hi and HiHi.lib/ote/databases
6Wire bindingsBuild the Sources → Bindings → Targets graph.lib/ote/bindings
7ValidateNaming, binding integrity, type mismatch, completeness, standards fit.lib/validation
8PackageWrite the databases, add the screens, repack as a native .eote.lib/ote/packager

Why the preview cannot lie

The browser canvas renders Screen.dat into SVG — the same JSON the packager writes into the file. One model, two renderers. What the engineer approves is what OTE opens, because there is no second representation that could drift.

We enforce it in the type system: the canvas switches exhaustively over the part union, so adding a part to the schema breaks the build until the canvas can draw it.

Where we meet the product

At the artifact boundary — we produce the files OTE already reads. We never touch its C# or C++ internals. That boundary is language-agnostic, so our stack and theirs never need to meet, and the tool works with any OTE 4.4+ install and survives upgrades.

The number that matters

HMICopilot_TS.eote — 25 KB, 19 parts, 7 tags, 5 alarms, 11 bindings, zero objects placed by hand. Written entirely by TypeScript running behind an HTTP endpoint, never saved by Schneider's software. It opens in EcoStruxure Operator Terminal Expert 4.4.

Section 08

Proven vs designed

Know the line before a judge finds it. Everything on the left has been run; everything on the right is architecture we can defend but have not finished.

Working, and verified

  • The .eote generator in Python and in TypeScript, producing structurally identical files
  • A generated project opening in OTE 4.4 with its screen, 7 variables, 5 alarms and 11 bindings intact
  • POST /api/export returning a real project file from a production build
  • Tag ingestion from csv / txt / xlsx with corrections reported, not silent
  • Validation against the product's own documented naming rules
  • 474 of the 475 shipped graphic objects converted to SVG path data
  • The canvas rendering a real Screen.dat in the browser

Designed, not yet built

  • The streaming generation pipeline — event contract is fixed, the model calls are not wired
  • Live Modbus / OPC-UA; a simulator drives the canvas today
  • Multi-screen projects with navigation between them
  • Customer standards packs
  • The full workspace UI — shell and canvas exist, the inspector and binding map do not

Deliberately out of scope: device driver configuration, PLC logic, panel download and safety-instrumented functions. Generated variables are internal, which keeps the demo hardware-free.
